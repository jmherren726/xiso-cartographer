## [Unreleased]

### Added

- Repository scaffold: README, contributing guide, agent guide, handoff and plan documents, ADR process, MR template, code owners and Dependabot config.
- MIT licence (ADR 0002).
- Host build: CMake presets (`host-debug` with ASan/UBSan, `host-release`), warnings as errors, clang-format and clang-tidy configs.
- Unity unit test framework (ADR 0003) and a first core test.
- GitHub Actions CI: format check, clang-tidy, and build + tests on Linux (gcc, clang) and Windows (cl, clang-cl).
- nxdk toolchain (pinned submodule) in a Docker build image, and a hello-world XBE that runs libxcat on the Xbox. CI builds it and uploads `default.xbe` and a bootable ISO.
- M0 complete: the hello XBE boots in xemu and on real hardware (docs/testing.md).
- Map file format v1 specification (docs/formats/map.md) and architecture document (docs/ARCHITECTURE.md).
- ADRs 0004 (streaming install over HTTP Range), 0005 (BearSSL for TLS) and 0006 (no links, no bypasses, good-guest networking).
- Synthetic xiso fixture generator (tools/fixtures/): small, deep, XGD1/XGD2/XGD3 full-disc and >4 GiB images from dummy data, with manifests; deterministic, sparse, and cross-checked against extract-xiso in CI.
- XDVDFS reader (`xc_xdvdfs_open`, `xc_xdvdfs_list`): detects trimmed xiso and full-disc XGD1/2/3 images, walks directory trees without recursion, rejects corrupt or hostile images (docs/formats/xdvdfs.md), and lists files in offset order. Plus `xc_err` error codes and the `xc_source` byte-source interface.
- ADR 0007 and the credentials file format (docs/formats/credentials.md): logins for sources that need them, stored as host-scoped tokens outside the map, sent only over HTTPS and re-checked on every redirect (design; implemented in M3–M6).
- libFuzzer target for the XDVDFS reader, with seeds generated from the fixtures. Every build replays the seeds; a `fuzz` preset and CI job run the fuzzer with ASan and UBSan.
- Extractor (`xc_extract`) and the `xc_sink` interface: directories first, then files in offset order through one caller-provided buffer, coalescing small gaps into a single read span (ADR 0004); progress reporting and cancellation. Output matches `extract-xiso -x` byte for byte.
- Host platform layer (`platform/host`): file source and directory sink, with UTF-8 and long-path support on Windows.
- `xcat-cli list` and `xcat-cli extract` for PCs.
- FATX probe XBE (`app/fatx-probe`): measures which names, paths and directory sizes the console's FATX driver accepts, so the M2 naming rules come from the real kernel.
- FATX rules measured on the console (docs/formats/fatx-names.md) and `xcat/fatx.h`: games whose files the Xbox hard disk can't store are refused, with every problem listed (ADR 0008); install folder names are generated from titles. `xcat-cli check` runs the same check on a PC.
- On-box install (M2): the XBE installs the images in `E:\xcat\isos\` to `E:\Games\<title>` with FATX and free-space checks, then reads every file back to verify it. A synthetic test image is bundled. Xbox platform layer (`platform/nxdk`): file source, FATX directory sink, free space, drive mounting.
- ADR 0009 (accepted): install from zip archives by streaming the zip with HTTP `Range` (Zip64, stored + Deflate, CRC-32 verified), based on archive.org tests showing that "file inside a zip" URLs can't be resumed and stop at ~1 GB.
- HTTP client profile (docs/formats/http.md): the strict HTTP/1.1 subset the console speaks, with limits, status handling, retries, resume and per-hop credentials.
- URL parser (`xcat/url.h`) and HTTP response parser (`xcat/http.h`): `http`/`https` URLs with percent-encoding and redirect resolution; response heads, `Content-Range` and chunked bodies, rejecting anything ambiguous. Both are fuzzed in CI.
- Stream-order report (`xc_xdvdfs_stream_order`, `xcat-cli layout`): shows whether every directory table precedes the files it describes, i.e. whether an image can be installed from a sequential (Deflate) stream in one pass (ADR 0009 open question).
- HTTP client (`xcat/http_client.h`) over the new `xc_net`/`xc_clock` platform interfaces (`xcat/net.h`): `Range` requests for one remote file, up to 5 redirects with per-hop credentials, keep-alive, timeouts, retries with jittered backoff and `Retry-After`, and resume after a dropped connection without delivering any byte twice. Detects servers that ignore `Range` and files that change mid-download. `xc_http_source` exposes a remote file as an `xc_source`. New error codes for network and HTTP failures.
- `xcat-cli get <url> <file>`: downloads a file over plain HTTP with the core client, on host sockets (`xc_host_net`, Winsock or BSD) and a monotonic clock (`xc_host_clock`). Shows retries, progress and MB/s; `--timeout` and `--attempts` tune the retry behaviour.
- Range test server (tools/testserver/rangeserver.py) with scripted faults: redirects, error statuses with `Retry-After`, dropped and stalled connections, `200` instead of `206`, chunked bodies, a file that changes mid-download. 24 end-to-end `get_*` tests run `xcat-cli get` against it in CI.
- Network test XBE (`app/net-test`, M3): downloads a test file from a PC over the LAN with the core HTTP client and reports progress, every retry (e.g. while the cable is pulled), average MB/s and the CRC-32, on screen and appended to `E:\xcat\net-test.log`. It resumes after a lost connection; a power cut starts it over (journaled resume is M4). Xbox networking (`xc_nx_net`, lwIP) and clock (`xc_nx_clock`) in `platform/nxdk`. `tools/testserver/make_test_file.py` makes the deterministic test file and prints its size and CRC-32.
- CRC-32 (`xcat/crc32.h`), the zip/zlib variant. `xcat-cli get` now prints the CRC-32 of the download.
- Credentials file parser (`xcat/credentials.h`, docs/formats/credentials.md): all-or-nothing parsing with line-numbered errors that name sections but never values, host patterns with no overlap between sections, and the per-hop rule (https, or plain http only to private IPv4 addresses with `allow_http = yes`). Plugs into the HTTP client, so credentials are decided again on every redirect hop. `xcat-cli get --credentials <file>`; a `401`/`403` after credentials were sent reports "login missing or expired for `[name]`". Fuzzed in CI (`fuzz_credentials`).
- Map file loader (`xcat/map.h`, docs/formats/map.md): entries with title IDs and variants, last-entry-wins duplicates, `@include` of local files and URLs (through a caller-provided fetch, with the path rules, depth, cycle and file limits of §5–§6), `@archiveorg` accepted with a "not supported yet" warning. A bad line is skipped and reported with its file and line; the rest of the map still loads. `xcat-cli map <file>` checks a map on a PC, following includes over HTTP. Fuzzed in CI (`fuzz_map`).
- Install journal format (docs/formats/journal.md) and module (`xcat/journal.h`): the image's identity (size, partition offset, listing digest, server validators) and one line per finished file with its size and CRC-32. Every line carries its own CRC-32, so a line torn by a power cut is ignored and that file is redone, while anything a power cut can't explain makes the folder off-limits instead of being reused. Fuzzed in CI (`fuzz_journal`).
- Streamed, resumable installs (`xcat/install.h`): one call reads the image's tables, checks FATX, picks a fresh folder or resumes one whose journal matches, checks free space, streams each span with a single HTTP Range request, journals every file after it is flushed to disk, reads every file back and compares its CRC-32, then writes the marker. Shared by the console (next) and `xcat-cli install <url|image> <games-dir> [title]`. A file that fails the read-back check is removed, so running the install again repairs it. Host file access for it (`xc_host_install_io`, with durable writes).
- M4 console app: the XBE installs every entry of `E:\xcat\map.txt` over HTTP (and, as before, every image in `E:\xcat\isos\`) through `xc_install`, with credentials from `E:\Apps\xcat\credentials`, retries that survive a pulled cable, and resume after a power cut. Images of 4 GiB and more install, because nothing but the game's files is stored. Progress and results also go to `E:\xcat\install.log`, with connection timings on each retry. Xbox file access for installs (`xc_nx_install_io`); the FATX sink flushes finished files to the disk.
- Return to the dashboard from the XBE with LT + RT + Back + Black (rocky5's shortcut), at any time, including mid-install; the install resumes next time. Progress shows the file being worked on ("file 1 of 3"), and MB/s counts only this run's bytes. The summary gives the write and read-back speeds separately.
- M4 exit test met on hardware: the over-4 GB `large` fixture installed over the LAN at ~8 MB/s, resumed after a power cut from its checkpoint at 1,216 MiB, and passed the read-back check (~18 MB/s).
- Resume inside large files (ADR 0011, amends ADR 0004 §4): every 64 MiB of a large file is flushed and recorded as a `part` checkpoint (journal format v1.1), and an interrupted install continues the file from its last checkpoint instead of from 0. A failed install keeps a checkpointed file for the next attempt. Sinks gain optional `sync`, `resume_file` and `suspend_file`; `xcat-cli install --checkpoint <bytes>` sets the interval (for tests).
- FATX file-size rule (fatx-names.md §4b): the console's FATX grows a file to at most 4,294,950,912 bytes (4 GiB − 16 KiB) on E:, measured with probe v4. Images with a larger file are refused like other FATX problems (`XC_FATX_PROBLEM_FILE_TOO_BIG`), and the `large` fixture's big file is now exactly that size. The same probe run (kernel 1.0.5838.1) confirmed the 250-character file path, and showed that this kernel accepts every name byte ≥ 0x80. The code keeps rejecting the 40 that kernel 1.0.4627.1 rejects.
- ADR 0012 (amends ADR 0005), M5's TLS trust decisions: BearSSL pinned at upstream master `7bea48e`. The full Mozilla root set (curl's `cacert.pem`) is built in, and `E:\Apps\xcat\cacert.pem` replaces it. SNTP sets the time for certificate checks, with the console's clock as the fallback only if it isn't earlier than the build time. Randomness on the Xbox comes from timing jitter plus a seed file. M5 also computes whole-image MD5/SHA-1 for trimmed xisos.
- TLS client (`xcat/tls.h`, M5): BearSSL (pinned submodule `third_party/bearssl`) behind an `xc_net` that runs TLS 1.2 over the plain TCP one, so the HTTP client takes `https` URLs through its `tls` slot. ECDHE with AEAD ciphers only (ChaCha20-Poly1305 first). Certificates are always checked against the trust anchors, the URL's host and the current time, which comes from a platform hook, as does the randomness (ADR 0012). Trust anchors load from a PEM bundle, all or nothing, within limits (fuzzed in CI: `fuzz_tls_anchors`). New errors say whether a certificate wasn't trusted, wasn't valid at the current time, or whether the time or the randomness was missing. TLS failures aren't retried.
- HTTPS on the PC: `xcat-cli get`, `map` and `install` take `https://` URLs. The built-in CA bundle is Mozilla's root store as curl publishes it (data of 2026-09-25, pinned by SHA-256 in `third_party/cacert/`), embedded at build time and decoded by the same loader as a replacement file. `--ca-file <pem>` trusts those CAs instead; `--now <unix-seconds>` sets the time certificates are checked at (for tests). `get` reports the negotiated TLS version and cipher suite. TLS failures name the reason and BearSSL's error code. Host randomness (`xc_host_entropy`: BCryptGenRandom, /dev/urandom) and clock (`xc_host_wallclock`).
- The Range test server speaks HTTPS with `--tls-cert`/`--tls-key`; 10 `get_https*` scenarios and `install_https` run against it with the test PKI.
- On a PC, connections try IPv4 addresses first, like the console: `localhost` resolving to `::1` first no longer costs Windows' ~2 s refused-connect delay per connection.
- HTTPS in the console's network test (`app/net-test`, M5): https URLs work with the built-in roots, or `E:\Apps\xcat\cacert.pem` instead. Before downloading it measures the CPU's ChaCha20-Poly1305 and AES-128-GCM speed with no network (`xc_tls_measure_ciphers`), shows the console's clock and the randomness it gathered, then reports the connect time and the TLS suite the server chose. `limit=` downloads only the start of a large file. The console's clock is refused if it's earlier than the XBE's build (`xc_nx_wallclock`). Randomness comes from timer-interrupt jitter, hashed in a new core entropy pool with the MAC, the clock and a seed file renewed on every start (`xc_entropy_pool`, `xc_nx_entropy_gather`; ADR 0012 §6). BearSSL and `tls.c` are built with `-O2` for the Xbox (`app/tls.mk`); nxdk otherwise compiles without optimisation.
- `tools/testserver/make_lan_cert.sh` makes a throwaway certificate for HTTPS from the PC to the console over the LAN; `rangeserver.py --tls-ciphers` sets which suite the server prefers (default: ChaCha20 first, like the console). The certificate scripts work in Git Bash.
- TCP tuning for downloads over the internet (M5): over a 60 ms path one connection to archive.org ran at 0.3 MB/s, while HTTPS on the LAN ran at 6.7 MB/s. Our `platform/nxdk/lwip/lwipopts.h` now goes ahead of nxdk's lwIP options:
  - a 120-segment (~168 KB) receive window with window scaling, up from 64 KB without;
  - 192 receive buffers in the network driver, up from 64;
  - SACK, so a lost segment is resent without waiting for a timeout;
  - 32-bit statistics counters.

  The Docker image builds nxdk's network library with these options (named build context `xcat-lwip`), and `app/lwip.mk` applies them to our sources. The network test ends each run with lwIP's counters (`xc_nx_tcp_counters_get`): window, frames and segments in and out, drops, bad segments, memory shortages.
- The network test shows, during a download, what each TCP connection agreed (`xc_nx_tcp_describe`): window scaling and its factors, SACK, the windows, the congestion window. The first run after the TCP tuning went from 0.3 to 1.0 MB/s from archive.org with no stalls, but stayed flat at what a 64 KB window allows. The misleading frame counters are gone from the `TCP:` line (nxdk's driver doesn't update them). On archive.org it showed window scaling on and the 167 KB window in effect, and still 1.1 MB/s. So the network test now also shows where the time goes (`xc_nx_recv_counters_get`, a `Reading:` line): how long the app waited for data and how full the receive window was whenever it read. From archive.org it waited 85% of the time with the window mostly empty: the console keeps up, and the data arrives too slowly, most likely because of lost packets.
- A PC on the same network with its adapter forced to 100 Mbit/s gets 8.0 MB/s from archive.org, so the packets are lost on the console. The network test now shows the console's link speed and duplex (`xc_nx_link_get`), counts the frames lwIP refused because its input mailbox was full (nxdk drops those without counting), and counts reads that found out-of-order data. On archive.org: full duplex, nothing refused, 1.7 MB/s. The receive window doubles to 240 segments (~336 KB, window scale 3) with 384 driver receive buffers, and the network test logs the TCP handshake time and the most receive buffers in use at once. With them: 1.8 MB/s at a 57 ms round trip, at most 244 buffers in use, so neither the window nor the driver's buffers limit it; segments lost on the way do. That meets M5's target of 1 MB/s.
- SNTP for the time that certificate checks need ([docs/formats/sntp.md](docs/formats/sntp.md), ADR 0012 §5): `xcat/sntp.h` builds a request with a random nonce, checks every answer (mode, version, leap indicator, stratum, kiss-o'-death, the echoed nonce, not earlier than the build time), makes up to 3 attempts and picks the time source: NTP, else the console's clock if it isn't earlier than the build (`xc_time_choose`). A UDP interface (`xc_udp` in `xcat/net.h`) with host and lwIP implementations, `xcat-cli ntp [server]`, a fake SNTP server with one end-to-end test per misbehaviour (`tools/testserver/sntpserver.py`, `test_ntp.py`), unit tests and a fuzz target. The console's network test asks `pool.ntp.org` (or `ntp=<server>` in `net-test.txt`; `ntp=off` skips it) before its first HTTPS connection and logs which time it used. "No acceptable time" now reads "Couldn't get the correct time (NTP server unreachable and the console's clock is wrong)".
- Whole-image MD5 and SHA-1 for trimmed xisos ([ADR 0004](docs/adr/0004-streaming-install.md) §5, [journal.md §7](docs/formats/journal.md#7-verification)): the installer reads such an image front to back in full, gaps and directory tables included, hashes every byte (`xcat/hash.h`, BearSSL), and reports both values; `xcat-cli install --md5/--sha1` fails the install with "The downloaded image doesn't match its published checksum" when one differs (`XC_ERR_IMAGE_HASH`). Journal **v1.2** adds `hash` records with the running state every 64 MiB, so a resume continues the hash instead of re-reading the image; a journal without one (v1.1) hashes from the first byte again. Full-disc layouts are still checked by size and CRC-32 only. The `.xcat-installed` marker records the hashes, the console logs them, and the installer XBE now links BearSSL.
- The console installer installs `https://` map entries (and follows `@include`s and redirects to https). The first one sets up TLS once, through a shared `xc_nx_https_start` (`platform/nxdk/src/nx_tls.c`), which the network test now uses too: randomness, the time from NTP (`pool.ntp.org`, or the first line of `E:\Apps\xcat\ntp.txt`, `off` to skip it; the console's clock otherwise, if not earlier than the build), the built-in roots or `E:\Apps\xcat\cacert.pem`. If that fails, the log says why and `http://` entries still install. Each HTTPS install logs the TLS suite. `docs/testing.md` has the M5 exit test (archive.org over HTTPS, a bad certificate, a wrong clock both ways).
- M5 exit test met on hardware: the archive.org test item installed over HTTPS (TLS 1.2, ChaCha20-Poly1305, time from NTP, built-in roots) at 1.4 MB/s, verified on read-back, with whole-image MD5 and SHA-1 equal to archive.org's. A wrong certificate, a clock years ahead and a clock earlier than the build with no NTP were all rejected (docs/testing.md).
- A server that answers plain HTTP on an https URL now gets "The server didn't answer in HTTPS (is it a plain http:// server?)" (`XC_ERR_TLS_NOT_TLS`) instead of a generic TLS failure. On Windows, `rangeserver.py` claims its port exclusively, so a second server can't start on a port that a stale one still answers.
- FATX probe v4 measures the largest file the console can store, and a failed install names the file it was on and, on the Xbox, which disk call failed with its error code. Both came out of the first M4 hardware run, where a 4,294,965,248-byte file failed at its end on the console but installs on a PC.
- Spool plan (`xc_xdvdfs_spool_plan`, xdvdfs.md §8.1), printed by `xcat-cli layout`: for a sequential (Deflate) install, how many bytes would have to be spooled to disk before every directory table is read, and how much a second pass would re-read for spools of 0 to 2 GiB. It sizes the hybrid planned for ADR 0009 (M5b) from more of the owner's games.
- ADR 0009 amendment 1 (owner decision): Deflate zip installs spool the bytes they can't identify yet to free disk (minus a reserve), keep the latest and drop the oldest 64 MiB chunks when space runs out, then re-read only the dropped late file bytes in a second pass. The extra cost is shown after pass 1. Based on `xcat-cli layout` measurements of 6 full-disc games.
- Zip directory reader (`xcat/zip.h`, spec in docs/formats/zip.md): finds the end records, Zip64 included, lists the central directory, chooses the zip's one `.iso`/`.xiso` image and checks its local header. Split archives, encryption and methods other than stored and Deflate are refused, naming the method (Deflate64, LZMA, ...). `xcat-cli zip <zip|url>` prints the entries and the image, also over HTTPS with a few Range requests. Fuzzed (`fuzz_zip`, also in CI), with zip fixtures generated from `small` (stored and Deflate).
- Reading zip members (`xc_zip_read_member`, docs/formats/zip.md §9–§10): stored and Deflate members are delivered in order through miniz's inflater (new pinned submodule `third_party/miniz` 3.1.2, tinfl only). The size, trailing bytes and CRC-32 are checked. The read can stop at any offset (for ADR 0009's second pass) and saves ~41 KiB checkpoints every multiple of 32 KiB to resume from. Checkpoints are tied to the build, CRC-protected, and checked against the member. Tested on stored, level 9 and level 0 zips of the `small` fixture, streamed and with `read_at`, with resumes from every checkpoint. Fuzzed (`fuzz_zip_inflate`, also in CI).
- Sequential extraction (`xc_seq_extract`, docs/formats/stream-install.md, ADR 0009 amendment 1): installs an image that can only be read front to back, as a Deflate zip member is. It finds the layout in stream order and parses directory tables as they pass, using the new `xc_xdvdfs_list_partial` (xdvdfs.md §9) with every listing check. Files whose directory is known are written as they pass; every other byte that might belong to a file is spooled into 64 MiB chunks on disk. When space runs out, the oldest chunk is dropped (while copying out, the farthest). Late files are copied out of the spool, and what the spool dropped is re-read in further passes, at most 16. New fixtures put tables after their files (`late`, `late-deep`, `late-xgd3`, `late-root`). `test_seq` installs them with roomy and tight disks; `fuzz_seq` checks every file byte for byte against the image (also in CI).
- Installing from zips (`xc_install_req.zip`, `xcat-cli install <file|url>.zip`, ADR 0009): the zip's one image is installed directly. A stored member is read with Range like a bare image, through the new `xc_source_window`. A Deflate member goes through sequential extraction, which spools into `.xcat-spool-<k>` files in the install folder (new optional `xc_install_io` spool callbacks; the host ones keep the file open). Pass 1 reads the whole member, so its CRC-32 covers every byte; later passes restart at an in-memory checkpoint and check their CRC-32s against pass 1's. Journal v1.3 adds a `zip` identity (journal.md §4.1, §6.8), so an interrupted install keeps its finished files. Refused zips name the reason: several images, LZMA and other methods, not a zip. Tests: 9 zip installs in `test_install` (one with a tight disk that needs a second pass); end-to-end over HTTP and HTTPS, resume after a kill, refused and damaged zips; `fuzz_journal` also reads zip journals.
- Resuming a Deflate zip install in the middle of the stream (stream-install.md §7, journal v1.4): at each zip checkpoint the engine saves its state (`xc_seq_save`): the tables captured so far, the spool's index and the file being written, after making both durable. `xc_install` keeps the checkpoints in `.xcat-zip-checkpoints` and the state in `.xcat-state-0`/`-1`, named by new `state` journal lines; `drop` lines record deleted spool chunks. A resume continues from the last state, reusing the spool files and the half-written file (`xc_seq_req.resume`, `xc_install_result.zip_resumed_at`); a damaged state or checkpoint file falls back to starting the stream again. New optional `xc_install_io.spool_sync` and `xc_seq_spool.size`/`sync` (the host io makes spool files durable when it switches files). `xcat-cli install` says how far into the image it continued. Tests: cuts at every checkpoint, in later passes and on tight disks (`test_seq`, `test_install`), killed installs over HTTP (`zip_resume_mid_stream`); `fuzz_seq` cuts and resumes, and resumes from forged states; `fuzz_journal` reads `state` and `drop` records. This also fixes two faults in the first zip install change: spool files left by an interrupted attempt were appended to instead of replaced (now deleted when no state continues them), and a failed Deflate install could read the name of the file it was writing after freeing it.
- The console installs from zips (M5b): map entries ending in `.zip` and `*.zip` files in `E:\xcat\isos\` install the zip's image, stored or Deflate, with the spool, later passes and mid-stream resume of the PC (`xc_nx_install_io` gains spool files, flushed before each saved state; `xc_nx_spool_close`). The log shows the zip's image, passes, MiB read again, spool size and where a resume continued, and names an unsupported method. `xc_zip_is_zip_name` (also used by `xcat-cli`). Map entries that point into a zip (`…/x.zip/y.iso`) are refused when the map loads (map.md §4.2, ADR 0009 §8). docs/testing.md has the M5b exit test; build-xbox.md describes zip installs.
- The console says when it found no credentials file (`E:\Apps\xcat\credentials`), points out a `credentials.txt` that should be renamed, and adds "no login was sent" to an access-denied error when none were loaded. Before, a missing file was silent, so a misnamed one looked like an expired login.
- M5b exit test on hardware, first run (docs/testing.md): a full-disc Zip64 Deflate zip from archive.org installed over HTTPS in one pass with a 1,590 MiB spool, 3.3 MB/s of image, verified, and the game launches. Second run, **M5b exit test met**: another full-disc Deflate zip, switched off at 1,155 MiB, resumed at 1,152 MiB from the saved state and spool, finished in one pass (3,350 MiB spool, 2.9 MB/s), verified, and the game launches.

- archive.org item listings (`xcat/archiveorg.h`, docs/formats/archiveorg.md, ADR 0013, M6): reads the answer of `https://archive.org/metadata/<item>` with a new strict, bounded JSON pull parser (4 MiB, nesting 32 deep) and chooses the item's original `.iso`, `.xiso` and `.zip` files, each with a name (the file name without its extension; generated entries are keyed by name, not title ID), a percent-encoded download URL, the size and whichever MD5, SHA-1 and CRC-32 are given. Missing (`{}`) and taken-down (`is_dark`) items are told apart; files with a bad name or size are skipped and counted. Unit tests and a fuzz target (`fuzz_archiveorg`, also in CI). M6 builds no PC login helper (owner decision): tokens go in the credentials file until M8's on-box login.

- Whole-file GET in the HTTP client (`xc_http_get`, docs/formats/http.md §3): no `Range`; a `200` with a chunked or `Content-Length` body, up to a limit, fetched again in full after a failure. archive.org's `/metadata` listings need it: they ignore `Range` and arrive chunked with no length. `@include` over HTTP now uses it too (in `xcat-cli` and on the console), so maps can come from servers without `Range` support.
- `@archiveorg <item>` in maps (map.md §5.2, archiveorg.md §7): the loader fetches the item's listing through its fetch callback and adds one entry per image file, keyed by name (`xc_map_entry.name`, found with `xc_map_find_name`) and carrying the listing's size, MD5, SHA-1 and CRC-32. Missing, taken-down and unreadable items are line errors that name the item; skipped files and malformed hashes are counted in warnings. At most 32 per load. `xcat-cli map` prints generated entries with their size and hashes. The console lists them (name and size) but doesn't install them yet, since one item can hold a whole collection. `fuzz_map` also serves listings.
- The console no longer installs everything it's given. The map (with the games `@archiveorg` lists) and `E:\xcat\isos\` form a catalog, shown as a text list: the D-pad moves and pages, A installs the highlighted game and returns to the list, and Back returns to the dashboard. Lines are marked once installed or failed. Owner decision: the map is a catalog to pick from. M8's UI replaces the list.
- Installs checked against an archive.org listing (archiveorg.md §8). `xc_install_req.expect_size` refuses a file of another size before anything is written (`XC_ERR_SOURCE_SIZE`). The console passes the listing's size and, for `.iso`/`.xiso` files, its MD5 and SHA-1, which are compared for trimmed xisos; a zip's own hashes aren't the image's, so they aren't passed.
- Title IDs: `xcat/xbe.h` reads an XBE certificate (docs/formats/xbe.md, fuzzed as `fuzz_xbe`). After verification, the installer reads the installed `default.xbe` and writes `title_id=` and `title=` to the marker (journal.md §7.1, now documented). The console and `xcat-cli install` print them, or why there are none.
- docs/testing.md has the M6 exit test.
- **M6 exit test met** on hardware (docs/testing.md): `@archiveorg` listed 137 games from the owner's item, a non-existent item gave "doesn't exist or was removed", and a picked full-disc Deflate zip installed over HTTPS at 2.2 MB/s, matched the listing's size, verified, and recorded its title ID from `default.xbe`; the game launches.
- Catalog design (M7): ADR 0014 picks the sources (Wikidata, CC0, for games; Redump's factual fields for releases, with title IDs from serials), leaves out box art, and keeps the pipeline in `tools/catalog/` with `catalog.bin` and `CREDITS.txt` as release assets built deterministically from hashed, uncommitted raw inputs. docs/formats/catalog.md specifies `catalog.bin` v1.0 (CRC-checked header, game and release records, a name index for name-keyed map entries, a string table, and every check a reader makes). tools/catalog/SOURCES.md records each source's terms; tools/catalog/README.md the title-ID and variant rules.
- Catalog reader (`xcat/catalog.h`, M7): checks a whole `catalog.bin` before use (size, version, CRC-32, layout, strings, order, name index; catalog.md §7), reads it in place without allocating, and finds releases by title ID and variant or by Redump name (for name-keyed `@archiveorg` entries), plus a simple search. New error `XC_ERR_CATALOG`. `xcat-cli catalog <file> [query | --title <id>[@variant] | --name <name>]`. Unit tests, a fuzz target (`fuzz_catalog`, in CI), and seeds written by the pipeline's writer `tools/catalog/catalog_bin.py`.
- Catalog pipeline (`tools/catalog/`, M7, ADR 0014): `fetch.py` caches Wikidata's answers and Redump's Xbox datfile, list pages and disc pages outside the repo (one request at a time, at least 1 s apart; disc pages fetched once); `build.py` checks the cache against `inputs.lock`, ties discs to datfile entries by SHA-1, takes title IDs from serials, joins releases to Wikidata games (Redump ID, unique name, shared title ID), derives variant names, applies `overrides.toml`, and writes `catalog.bin`, `CREDITS.txt` and a review report, the same bytes on every machine. `--previous` reports changed variants. Tested on a synthetic cache, whose catalog `xcat-cli` also opens (CTest `catalog_pipeline`).
